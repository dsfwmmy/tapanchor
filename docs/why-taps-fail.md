# 点击成功了，然后什么都没发生

> 手机自动化最容易被忽略的一类故障：动作发出去了，界面没变，而框架告诉你一切正常。

---

## 一个所有写过自动化的人都遇到过的场景

我第一次撞上这件事，是在学习通上。

脚本要点开一道单选题的选项 A。无障碍树里有节点、有文字、bounds 正常，`click` 返回成功。日志一切正常。

然后它点了「下一题」。

交卷的时候系统提示：还有未做完的单选题。回头看才发现，二十道选择题，一个答案都没选中。

不是脚本崩了，是脚本**以为成功了**。那个 tile 是自绘的，点击事件被外层滑动容器吃掉，`performAction` 依然返回 `true`——因为事件确实投递出去了，只是没人消费。而我的脚本因为「点击成功」，一路往下跑完了整场考试。

这类故障还有个更常见的形态：你写了一个脚本，打开设置，点「显示与亮度」，断言进入二级页面。运行，日志一切正常。

```
tapOn: "显示与亮度"   ✓
assertVisible: "亮度"  ✓
```

但实际上什么都没发生——脚本点在了空白处，或者点到了一个不可点击的容器上，或者点了但页面正在做入场动画、点击被吞了。

更糟的是那些「看起来成功」的情况。Maestro 的 issue #2448 里，用户报告 `tapOn` 机械返回成功，底部 tab 根本没跳转。AutoJs6 的 issue #224 更直接：`click` 不生效，只有强制 `sleep` 一段时间之后才生效。

社区里有人做过实测：在 MIUI 上跑 `text("xxx").click()`，**50 次里成功 13 次**。剩下 37 次，全部静默失败——没有报错，没有异常，脚本继续往下跑，然后在三步之后以一个看似无关的错误崩掉。

这类故障有个共同特征：**它不报错**。

---

## 为什么会这样：三层原因

### 第一层：click 只是"投递事件"，不是"执行动作"

Android 的无障碍服务提供 `ACTION_CLICK`。但它的语义是「我请求这个节点被点击」，不是「这个节点被点击了」。

请求会被投递给目标 View，然后：
- View 可能不在前台（被遮挡、在滚动区域外）
- View 可能不可点击，只是恰好有文字
- View 的点击监听器可能因为业务逻辑提前 return
- 事件可能被父容器拦截（触摸分发）

系统没有任何机制告诉你「请求被拒绝了」。`performAction` 返回 `true` 只代表**投递成功**。

这是设计使然，不是 bug。

### 第二层：自绘控件没有语义节点

Compose、Flutter、WebView、Canvas 画出来的界面，在无障碍树里往往只有一层壳。Compose 下 `className("android.widget.Button")` 完全不适用，因为根本没有 Button 这个类。

AutoJs6 的 issue #269 里有个典型：`bounds` 返回 `[952,1036-1024,1108]`——格式错乱，解析出来是负面积，永远点不上。这类情况在国产 ROM 的定制控件上尤其常见。

Maestro 的 issue #2293 是同一类问题：WebView 里的 id 认不出来。

### 第三层：点击之后，界面不是立刻变的

点击 → 触发网络请求 → 加载 → 渲染 → 动画结束。这个链条在真机上常常是 300ms 到 2 秒。

如果你点完立刻抓树，抓到的是旧界面。如果框架认为「点完就算完成」，那它下一步就会在旧界面上操作。

## 现有框架怎么处理的（以及为什么不够）

**命令式方案（AutoJs6 / AutoX.js）**：把责任交给用户。你自己写 `sleep(1000)`，你自己判断有没有跳转。写得好的脚本里，等待和重试逻辑比业务逻辑还长。

**声明式方案（Maestro）**：有 `waitForAnimationToEnd`，最近才在 PR 里补上 settle 和分片重试。但 settle 的语义是「等界面稳定」，不是「验证你想要的结果出现了」。界面可能很稳定地停在一个错误的地方。

**AI 视觉方案（midscene 等）**：能识别「这个按钮在哪」，但每次调用都要烧 token，而且结果不确定——同一个界面两次识别可能给出不同的坐标。它解决的是「找得到」，不是「点得准」。

**Appium**：工程化最完整，但等待策略仍然要用户手写显式等待（explicit wait）。它给你工具箱，不给你判断力。

这四种方案的共同点：**它们都只保证「动作发出去」，把「动作有没有生效」留给了使用者**。

## 换一个立场：把「界面变了没有」变成验收条件

如果 click 注定只是投递请求，那唯一的出路就是：**每次动作之后，验证世界是否真的变了。**

这个想法本身不新鲜，Airtest 有截图对比，Playwright 有 auto-waiting。但在 Android 原生自动化这一层，它没有被做成默认行为。

具体怎么做：

### 1. 界面指纹

每次动作前抓一次无障碍树，算一个指纹：

```python
signature = frozenset((node.ident(), node.bounds) for node in tree.nodes() if node.label)
```

动作后再抓一次，比较是否相同。不同 → 世界变了。相同 → 什么都没发生。

这个指纹很粗，但它抓的正是最关键的信号：**有没有任何东西动了**。

### 2. 更精确的断言

指纹只能回答「变没变」，回答不了「变对了没」。所以要允许更细的断言：

```yaml
verify:
  text_exists: "亮度"      # 想要的文字出现了
  pkg: com.android.settings # 还在设置里，没被跳到别处
  count: {text: "开关", min: 3}  # 数量对得上
```

不写断言时，默认就是「界面必须变化」。这是最保守、也最贴合真实痛点的默认值。

### 3. 降级链

验收不过怎么办？不是直接报错，而是换一种打法：

```
精确文本 → 模糊文本 → 描述 → resource-id → 长按 → 坐标兜底
```

每换一种，重新抓树，重新验收。

在 MIUI 那种「第一次点不中」的机器上，这条链的实际效果是：第一下不生效，第二下（长按）生效了。人手动操作的时候其实也是这样——点一下没反应，你会再点一次，或者按住。

### 4. 全失败要留证

所有打法都失败之后，不能只抛一个 `AssertionError`。要留下：

- 截图（当时的屏幕长什么样）
- 无障碍树 XML（当时的节点长什么样）
- 每一步用了什么打法、卡在哪里

这条最不起眼，但在真实使用里价值最高。凌晨三点的定时任务挂掉，第二天早上你打开日志，看到的不是「step 7 failed」，而是当时那张截图。

## 实现时踩到的几个坑

### 坑一：脏树必须先洗

`uiautomator dump` 出来的 XML 是给机器看的，不是给人看的。直接在上面查节点会遇到：

- `bounds` 非法（`[0,0][0,0]`、格式错乱、负面积）
- 父子节点 bounds 完全相同，文字在里层，可点击在外层
- 大量既无文字又无子节点的空容器

所以要有一步清洗：

```python
# 1. 丢掉 bounds 非法或面积为 0 的
# 2. 合并 bounds 完全相同、且自己没有文字的父子（把壳拆掉）
# 3. 丢掉既无文字又无子节点的容器
# 4. 给每个节点算稳定标识：文本 → 描述 → resource-id 末段 → 类名
```

洗干净之后，同一棵树的节点数常常从几百降到几十，查找也稳得多。

### 坑二：adb 环境下没有「语义 click」

这点很多人搞混。通过 adb 你只能 `input tap x y`——就是往屏幕上戳一个坐标。所谓「点某个元素」，实际是：找到节点的 bounds → 算中心点 → 戳那个坐标。

所以「语义 click」这种说法在 adb 场景里是不成立的。真正的语义点击要用无障碍服务的 `performAction`，那需要一个常驻 App。

这决定了降级链的设计：你没法「换一种点击事件」，只能「换一种找目标的方式」+「换一种手势（点/长按）」。

### 坑三：每次抓树都很慢

一次 `uiautomator dump` 在真机上要 1–3 秒。加上动作和等待，单步 2–8 秒是常态。

这意味着：**这套方案不适合高频交互的场景**，适合「步骤不多但要跑得稳」的流程。想做几百次点击的压测，得换别的路子。

## 选择器自愈：为什么只做半自动

App 改个文案，脚本就挂。这是自动化最日常的死法。

自然的想法是：让模型自动改选择器。我试过这个方向，最后收窄成了半自动，原因是**信任**。

全自动自愈一旦改错一次（把「取消」识别成了「确认」），用户对工具的信任会一次性崩掉。而修复这种信任的成本，远高于省下来的那点人工。

所以现在的做法是：

1. 失败时，用编辑距离 + 可点击性 + 尺寸，从现场算出「最像的 3 个目标」
2. 人看一眼，选一个
3. 结果写进选择器库，下次这一步优先用它

真机上跑过一次：故意把「显示与亮度」写成了「显示和亮度」，第一次跑挂掉，现场给出候选 `text='显示与亮度' 相似度 0.88`；选完写回，第二次跑直接一次点中。

候选打分**不调用任何模型**——离线、零成本、每个结果都能解释为什么是它。这一点比「聪明」重要。

---

## 它不适合什么

诚实地说清楚边界：

- 不做自然语言规划。那层有阿里的 Mobile-Agent、droidrun 在做，而且做得很好。这里只做「手」。
- 不做并发和多设备编排。那需要机房和运维，个人做不了。
- 不适合高频操作（单步 2–8 秒）。
- 中文输入需要 ADBKeyboard 或剪贴板通道，`input text` 只支持 ASCII。

```bash

python -m tapanchor --serial <手机IP>:<端口> run flows/demo.yaml

# 手机本地跑（不用电脑）
./run_local.sh run flows/demo.yaml
```

如果你也被「点了没生效」折磨过，欢迎把你的 flow 和失败现场丢过来。真实设备的脏树样本，比任何设计讨论都有用。

## 最后一句

自动化最难的不是让程序动起来，是让程序知道自己有没有动对。

大部分框架把这个问题留给了使用者。这篇文章想说的是：它应该被当成一等公民，写进每一个动作的验收条件里。
